## What you can rely on

- `apps/web/src/game-objects/render-projection.ts` is the one place that decides
  what a GameObject draws, and it decides it from Components. It is pure — no
  React, no Three — so anything you need to assert about rendering can be
  asserted in Node.
- `GameObjectRenderer` takes a `RuntimeGameObject` or a projection. It is
  already the Prefab Editor's viewport. Pointing the Scene viewport at it is a
  matter of handing it `RuntimeScene.gameObjects`, not of writing a renderer.
- `browserPrefabRegistry()` gives the browser a real `PrefabAssetRegistry`
  (documents now ship in `generated/prefab-assets/library-index.json`). No API
  server needed to resolve a Prefab.
- `LEGACY_CHARACTER_PREFAB_IDS` in `packages/schema/src/migration.ts` is the
  only legacy Character→Prefab table. Do not add a second one.
- `harness:game-object-renderer` is in `harness:one-shot`.

## Where to pick up — step 3, and why it is all-or-nothing

The next step is the Scene runtime and Scene Editor cutover, and it **cannot be
half done**. Switching the Scene viewport to `RuntimeScene` while the Scene
Editor's operations still write `entities` gives two answers to what is in the
Scene, free to disagree — the parallel entity runtime §5 forbids. That is why
this session stopped here rather than landing a viewport change that looked like
progress.

So step 3 and step 4 land together:

1. `use-scene-session` / `SceneEditorPage` resolve through
   `resolveSceneGameObjects()` + `instantiateScene()`; the viewport iterates
   `RuntimeScene.gameObjects` and renders each through `GameObjectRenderer`.
2. Hierarchy rows become GameObjects (enabled, name, Prefab id/version, Component
   badges, instance-override badge) with Prefab nodes and nested Prefabs
   expandable.
3. The thirteen `scene.*` GameObject operations replace the entity operations,
   including the two behaviours that are easy to miss:
   `set_prefab_source` clears incompatible instance overrides (node/component
   identities belong to the old Prefab graph), and `duplicate_game_object` does
   **not** copy camera relations.
4. The repository apply path loads the canonical Scene, validates, applies to
   `gameObjects`, revalidates and writes through the existing transaction. No
   production operation may write `entities`.

Only once Web and runtime read `gameObjects` do steps 5–8 (APIs, adoption,
`AnimationSubjectDefinition`, canonical deletion) become safe. Deleting the
legacy schema before that is what failed last time; §2 of the work package and
DECISION 0024 both say so.

## Traps found in this session

- `walk()` returns the node and its descendants; each child node is its own
  `RuntimeGameObject` with its own id (`<instanceId>/<nodeId>`). Selection and
  gizmo targeting in the Scene Editor need to decide whether they address the
  instance or a node inside it — the instance is the thing a Scene operation can
  name.
- A simulated node (one with a `CharacterMotor`) reports the simulation's world
  transform and is not carried by its parent. A Scene gizmo that writes a world
  transform onto such a node is writing to something the simulation overwrites
  next tick.
- The Prefab index is regenerated by `assets:prefabs:index` and checked by
  `harness:prefabs`; its schema version is now 2 because it carries documents.
- The visual suite is slow under swiftshader (multi-megabyte GLB loads). Budget
  for it, and do not assume a hang is a failure.
